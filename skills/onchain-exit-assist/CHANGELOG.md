# CHANGELOG：onchain-exit-assist

## v1.0（2026-10-17）

狀態：草稿定稿，驗收通過（派工 13 PASS）。還沒發佈，也還沒安裝。

### 這個 skill 做什麼
幫使用者「看清楚、準備好」鏈上退場。所有交易都由使用者自己在錢包裡確認、簽名、送出。
- 多鏈資產盤點：原生幣、token、協議部位；沒掃到的標「未知」。
- 授權盤點與分級：ERC-20／NFT 授權、Permit2；產生撤授權卡。
- 退場卡、路線卡：先模擬，再由使用者自己簽。
- 期限監控：需要使用者同意。
- 每份報告和每張卡都附「這次把地址送到哪些服務」，並註明「完成後鏈上要核對」。
- 硬限制：
  - 不碰私鑰、助記詞；不代簽、不廣播。
  - 地址不貼到搜尋引擎或公開社群。
  - 不把金鑰、API 金鑰或簽名送到任何地方。

### 審查回合與修改

**第 1 輪（研究審查 H1–H3、M1–M16、L1–L17）**
- 地址外送改成兩層揭露。
  - 預設允許送到第三方服務，只問一次：「要不要允許把地址送到第三方服務？」
  - 使用者拒絕時，只用 RPC 節點和協議官方端點。
- 卡片優先順序：官方 dApp ＞ 官方區塊瀏覽器 ＞ 第三方工具（要標明「第三方」），並寫明「連上錢包就會把地址交給那個網站」。
- Multicall 讀取失敗時標 UNKNOWN，不當成 0。
- 模擬時沒有任何斷言，不算 PASS。
- Permit 類簽名一律警告。
- 監控要先取得同意；警報觸發後要重新模擬。
- SIWE 要有到期時間；期限處理考慮 UTC+14。
- 拿掉「全鏈」「安全退出」這類過度承諾的字眼。

**第 2 輪（ACCEPT-1～5）**
- `rpc.py`：
  - 讀取方法白名單，預設拒絕，方法名稱先做 NFKC 正規化；
  - 批次請求逐筆檢查；
  - 擋掉內部路徑和夾帶的方法。
- `get_logs_chunked.py`：
  - 涵蓋範圍有缺口時，`log_count` 是 UNKNOWN，結束碼不是 0；
  - 重試有次數和時間上限；
  - 被限流時不切半。
- `simulate.py`：
  - 原生幣的預期支出 = 宣告的 value + gas；
  - owner 有程式碼時會標出來（含 EIP-7702 委派，`0xef0100` 開頭）。
- `decode_sign_request.py`：
  - SIWE 要嚴格符合 EIP-4361 格式；
  - 缺少到期時間、出現危險字眼都直接 REJECT。
- `address_audit.py`：能抓到黏在其他字上的地址、32-byte 補零的地址、沒有 0x 前綴的地址。

**第 3 輪（單一檢查點）**
- `rpc.py` 的 `_post` 是唯一的送出點，檢查的是實際送出的內容。紀錄用的方法標籤也從實際內容取得，不信任呼叫端給的值。
- 驗收員的 77 種繞過情境全部擋下。

**第 4 輪（review2：N1、N2 與 LOW）**
- N1：`disclosure()` 依實際送出的內容，把每筆請求分成三類：
  - 完整錢包地址；
  - 只有合約或其他地址；
  - 只有區塊號或無地址。

  要先用 `register_wallets()` 登錄錢包才分得出前兩類，沒登錄時標「可能含錢包地址」。另外新增 `disclosure_log.py`，記錄腳本以外的外部請求，並產生「這次把地址送到哪些服務」表格。
- N2：模擬的交易筆數或區塊數，和節點回傳的結果數對不上時，判 FAIL／UNKNOWN，不會 PASS。
- chainId 改成必填，每個 RPC URL 用前都核對，沒有關閉的選項。
- 撤授權卡的揭露範本列出主要網站和兩個備案，第三方要標明。
- spender 地址要從協議官方文件或官方合約清單複製，不從事件頁或聊天紀錄複製。交易後仍要確認 allowance = 0。

**X-1（address_audit 邊界規則）**
- 白名單、公開或範例地址，只有前後都不緊鄰 hex 字元時才算數。前面（含 0x 前面）或後面多黏任何 hex，整串標 REVIEW。

**派工 13（disclosure_log.py）**
- 每個欄位都用同一套規則檢查，包括 path、service、host、endpoint、purpose、when、kind、render 的 wallet_sites，以及讀回紀錄時的每一筆。檢查前先做 NFKC，全形字會轉成一般字。
- `when` 只收 ISO-8601 或 epoch 秒。
- 助記詞：內建官方 BIP-39 英文字表（2048 字），import 時會核對字數和 sha256。連續 12 個以上 BIP-39 字一律拒絕。
- 英文關鍵字以整個 token 比對：會拆 camelCase，連字號和底線都算分隔。
  - `sig`、`access token`、`bearer`、`authorization` 只在後面接值時才擋，例如 `sig=`、`access_token=`、`Bearer <值>`、`Authorization:`。
  - 中文關鍵字（私鑰、助記詞、簽名、金鑰、密碼等）照擋。
- 長字串規則：
  - 0x 或裸 hex 連續 32 個以上就擋；
  - 32 字元以上、混合大小寫和數字的 base58／base64／base64url 也擋；
  - 路徑會逐段判斷；
  - 用連字號分隔、每段都像單字而且 ≤12 字的識別名稱放行（例如 ERC20-Permit2-allowance-check-v2）。
- 本版最後一項修正：含 `/` 的標準 Base64，會先把整串（含 `+`、`/`、`=` 補位）當成候選長字串判斷。只有每一段都像單字時，才當成路徑。
  - 修正前約 28% 的 32-byte 隨機 Base64 會被放行，修正後在測試樣本中 100% 擋下。
  - `/docs/<識別名稱>` 照常放行，`/verify/<長字串>` 照擋。

### 已知限制
- 助記詞：
  - 連續 11 個或更少的 BIP-39 字不會被擋。
  - 黏在一起的 BIP-39 字不會被擋，不論是 camelCase（例如 abandonAbility…）還是全小寫。
  - 只寫前 4 個字母的寫法不會被擋。
  - 不是英文字表的助記詞（例如中文字表）不會被擋。
- hex 被空白或連字號切成每段都不到 32 個時，不會被擋。
- Base64 被空白切成短段，或做了百分比編碼（`%2F`、`%2B`、`%3D`）時，不會被擋。
- 沒有數字、但帶 `-` 或 `_` 的 base64url 長字串會放行（隨機樣本約 0.07%），因為判斷 base64url 長字串時仍沿用「一定要有數字」的舊規則。之後再修。
- 偏保守的誤擋，目前仍會擋下：
  - `apikeys docs page`、`bearer bonds`、`key store hours`、`pass word game`；
  - 連字號識別名稱裡有超過 12 字的段落；
  - 32 字元以上、混合大小寫和數字、又沒有連字號的長 camelCase 識別名稱。
- 紀錄欄位裡連公開合約地址和交易雜湊也一律拒絕，請用 `{addr}`、`{hash}` 這類佔位字。
- `when` 只收 ISO-8601 或 epoch 秒。
- `disclosure()` 要先登錄錢包，才能分辨「完整錢包地址」和「只有合約地址」。沒登錄時一律標「可能含錢包地址」。
- `address_audit.py` 只是啟發式檢查，PASS 只代表「沒找到已知的格式」。它無法判斷私人標籤、餘額、文字裡的人名或截圖。
- N6（簽名請求解碼時的授權標示）還沒處理。
- 非 EVM 鏈和鏈下帳戶只列出來，不會自動掃描；沒掃到的一律算「未知」。
